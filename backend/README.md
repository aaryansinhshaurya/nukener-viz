# NER Review Platform — Backend (Module 1 + 2 + 3 + 4)

## What's in this build

**Module 1 — Auth + Projects + Roles**
- User signup/login with JWT (access + refresh tokens)
- Password hashing with bcrypt (direct, not passlib — see note below)
- Project creation (creator becomes Owner automatically)
- Project membership with roles: Owner / Reviewer / Viewer
- Projects are private — `GET /projects` only ever returns projects you're a member of
- Invite a registered user to a project by email + role (Owner only)

**Module 2 — Data Ingestion**
- Upload a CSV or JSON file to a project (**Owner only**) — parses into the
  Project → Document → Sentence → Entity tree
- Supports the `entities` column as either JSON or a Python literal
  (single-quoted dicts, like your original sample data) — both are handled
- **Validates every entity's `start_char`/`end_char` against the actual
  sentence text at upload time**
- `GET /projects/{id}/documents` — list documents with sentence counts
- `GET /projects/{id}/documents/{doc_id}` — full sentence + entity tree
- One upload per project in this module — re-uploading is Module 5's job

**Module 3 — Review Workflow (TP / FP / FN)**
- `POST /projects/{id}/entities/{entity_id}/review` — mark a model-predicted
  entity **True Positive** or **False Positive** (Owner or Reviewer only)
- `POST /projects/{id}/documents/{doc_id}/sentences/{sentence_id}/missed-entity`
  — click-and-drag flow: report a missed span as a **False Negative**
- Reviews are **append-only** — changing a verdict adds a new row, full
  history preserved automatically
- `GET /projects/{id}/entities/{entity_id}/reviews` — full review history
- The document tree (Module 2) now returns each entity's current review
  status and reviewer attribution in the same call

**Module 4 — Metrics Engine**
- `GET /projects/{id}/metrics` — project-wide Precision/Recall/F1
- `GET /projects/{id}/documents/{doc_id}/metrics` — same, scoped to one document
- Computed **live** on every request directly from the reviews table —
  nothing cached or batch-computed, so it's never stale
- Also returns `percent_reviewed`, `total_model_entities`, and raw
  `tp`/`fp`/`fn` counts alongside the computed ratios, so an incomplete
  review never gets misread as a finished score
- **Precision/Recall only ever apply to model-predicted entities** —
  human-added (FN) entities can't be TP/FP by definition, so they're kept
  out of that side of the math and only contribute to the FN count. This
  is exactly why Module 2/3 track `source` (`model` vs `human`) on every
  entity — it's what keeps this calculation correct
- `precision`/`recall`/`f1` are `null` (not `0`) when there isn't enough
  data yet to compute them meaningfully — e.g. a document with zero
  reviews shows `null`, not a misleading `0.0`

## Setup

### 1. Create a Neon Postgres database
Go to https://neon.tech, create a free project, and copy the connection string from
the dashboard (it looks like `postgresql://user:pass@host/dbname?sslmode=require`).

### 2. Set up the Python environment
```bash
cd backend
python -m venv venv
source venv/bin/activate        # on Windows: venv\Scripts\activate
pip install -r requirements.txt
```

### 3. Configure environment variables
```bash
cp .env.example .env
```
Then open `.env` and paste in your real `DATABASE_URL` from Neon, and generate a
real `JWT_SECRET_KEY`:
```bash
python -c "import secrets; print(secrets.token_hex(32))"
```

### 4. Create the database tables
```bash
alembic revision --autogenerate -m "create users, projects, documents, reviews tables"
alembic upgrade head
```
(Module 4 adds no new tables — metrics are computed live from the
`reviews` table, not stored anywhere.)

### 5. Run the API
```bash
uvicorn app.main:app --reload
```

### 6. Test it
Open **http://127.0.0.1:8000/docs** — Swagger UI, auto-generated by FastAPI.

## Manual test walkthrough

### Module 1 (repeat this first if you haven't already confirmed it)
1. `POST /auth/signup` — create User A (e.g. `alice@example.com`)
2. `POST /auth/signup` — create User B (e.g. `bob@example.com`)
3. `POST /auth/login` as User A — copy the `access_token`
4. In Swagger, click **Authorize** and paste: `Bearer <access_token>`
5. `POST /projects` — create a project as User A (becomes Owner)
6. `GET /projects` — shows the project for User A
7. Log in as User B, authorize with their token, `GET /projects` — empty list
8. As User A: `POST /projects/{project_id}/invite` with Bob's email, role `reviewer`
9. As User B: `GET /projects` — the project now appears
10. As User B: try `POST /projects/{project_id}/invite` — `403 Forbidden`

### Module 2 (new)
11. Prepare a CSV using your real format — **make sure every entity includes
  `start_char` and `end_char`** matching where that span appears in the
  sentence. The backend will normalize casing from the offsets when it can.
  Example row:
    ```
    doc_id,sentence_id,sentence,entities
    D085,D085-S053,"The statement also acknowledges the role of private investment in accelerating fusion development...","[{'text': 'private investment', 'label': 'Investment and Funding', 'start_char': 44, 'end_char': 62}]"
    ```
12. As User B (Reviewer role): `POST /projects/{project_id}/upload` with that
    CSV file attached — should get **403 Forbidden** (only Owners upload)
13. As User A (Owner): same upload — should get **201** with a summary:
    `{"documents_created": 1, "sentences_created": ..., "entities_created": ...}`
14. `GET /projects/{project_id}/documents` — shows the document with a
    sentence count
15. `GET /projects/{project_id}/documents/D085` — returns the full sentence +
    entity tree, ready for the frontend to highlight
16. Try uploading the same file again — **400 Bad Request**, explains that
    re-uploading isn't available until Module 5 (versioning)
17. Try uploading a CSV where an entity's offsets point to the wrong
    substring — **422 Unprocessable Entity**, tells you exactly which
    sentence and entity is wrong

### Module 3 (new)
18. As User B (Reviewer): `GET /projects/{project_id}/documents/D085` and
    grab an `entity_id` from the response — its `current_review` should be
    `null` (nobody's reviewed it yet)
19. As User C (Viewer, invite them first with role `viewer`):
    `POST /projects/{project_id}/entities/{entity_id}/review` with
    `{"verdict": "TP"}` — should get **403 Forbidden**
20. As User B (Reviewer): same call — should get **201**, with the
    verdict, your user id, and a timestamp
21. `GET /projects/{project_id}/documents/D085` again — that entity's
    `current_review` now shows the verdict and reviewer name
22. Submit a *second* review on the same entity with a different verdict
    (e.g. `FP`) — succeeds, and `GET /entities/{entity_id}/reviews` shows
    **both** rows, most recent first — nothing was overwritten
23. `POST /projects/{project_id}/documents/D085/sentences/{sentence_id}/missed-entity`
    with a `text`/`label`/`start_char`/`end_char` for a real span of plain
    text in that sentence — **201**, returns a new entity with
    `"source": "human"` and an automatic `"verdict": "FN"` review attached
24. Try the same call with offsets that don't match the given `text` —
    **422**, tells you exactly what text those offsets actually point to
25. Try reporting a missed entity that overlaps an existing highlighted
    entity — **400**, tells you to review the existing one instead
26. Try submitting a TP/FP review on the human-added entity from step 23 —
    **400**, explains it's already recorded as FN

### Module 4 (new)
27. Before reviewing anything in a fresh document: `GET
    /projects/{project_id}/documents/{doc_id}/metrics` — `tp`, `fp`, `fn`
    all `0`, `percent_reviewed: 0.0`, and `precision`/`recall`/`f1` all
    `null` (not `0` — nothing's been reviewed yet, so there's no ratio to
    show)
28. Mark a few entities TP and a couple FP, add one missed entity (FN),
    then hit the same metrics endpoint — `tp`/`fp`/`fn` reflect exactly
    what you marked, and `precision`/`recall`/`f1` match what you'd
    compute by hand: `precision = tp/(tp+fp)`, `recall = tp/(tp+fn)`
29. `GET /projects/{project_id}/metrics` (no document in the path) —
    returns the same numbers aggregated across every document in the
    project
30. Leave one document's entities completely unreviewed and check its
    `percent_reviewed` is `0.0` while a fully-reviewed document shows
    `100.0` — confirms coverage is tracked per document, not guessed

If all steps behave as described, Modules 1–4 are solid. Next up: Module 5
(Locking + Versioning) — document-level locking for concurrent reviewers,
and the Save/Timeline/Revert flow.

## Known simplifications (by design, not oversight)

- **Inviting a not-yet-registered email** returns a 404 telling them to
  sign up first. A real "pending invite, they get a signup link" flow is
  a fast follow-up.
- **Refresh tokens aren't revocable yet** — no denylist/rotation.
- **One upload per project** — re-upload/versioning is Module 5's job.
- **Labels are free-text**, taken as-is from the input file — no taxonomy
  enforcement, per your call in the spec review.
- **No document locking yet** — two reviewers can review the same
  document (even the same entity) at the same time in this module. That's
  Module 5's job, not a bug here.
- **No adjudication/disputed queue** — if two reviewers give conflicting
  verdicts on the same entity, both are simply preserved in the history;
  nothing automatically flags a conflict yet.
- **No per-label metric breakdown** — metrics are TP/FP/FN totals only,
  not split out by entity label (e.g. separate F1 for "Organization" vs
  "Investment and Funding"). Straightforward to add later by grouping the
  same query by `label` if you end up wanting it.
